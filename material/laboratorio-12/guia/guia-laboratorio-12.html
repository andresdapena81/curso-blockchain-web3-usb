Paso 2 · Servir la página (y por qué el doble clic no sirve)

5 MIN

Si abren index.html con doble clic, el navegador lo carga como file:///C:/…/index.html. Con MetaMask eso falla, por dos razones:

  • Chrome no deja actuar a las extensiones en páginas file:// salvo que el usuario active, extensión por extensión, «Permitir acceso a URL de archivo». Viene apagado. Sin eso, MetaMask no inyecta window.ethereum y la dApp dice «No se detecta una billetera».
  • MetaMask da permisos por sitio (por origen: esquema + dominio + puerto). Una página file:// no tiene un origen normal, así que la conexión es poco fiable aunque se active el permiso.
NO ACTIVEN «PERMITIR ACCESO A URL DE ARCHIVO»

Le daría a la extensión acceso a archivos de su disco. La práctica correcta es la misma que en producción: servir la página por HTTP. En local, por http://localhost.

Opción A · con Node (la primera vez npx pregunta si descarga el paquete serve: respondan y):

cd "ruta\a\material\laboratorio-12\andamiaje"
npx serve .
   ┌──────────────────────────────────────────┐
   │   Serving!                               │
   │   - Local:    http://localhost:3000      │
   └──────────────────────────────────────────┘

Opción B · con Python (si la sala no deja descargar serve):

cd "ruta\a\material\laboratorio-12\andamiaje"
python -m http.server 8000
Serving HTTP on :: port 8000 (http://[::]:8000/) ...

Abran http://localhost:3000 (opción A) o http://localhost:8000 (opción B). Dejen esa terminal abierta: si la cierran, la página deja de cargar.

Paso 4 · Configurar la dApp y punto de control

5 MIN

4.1 · Pegar la dirección y la red. Abran andamiaje/index.html en VS Code. Casi al final, en la sección CONFIGURACIÓN:

const DIRECCION_FICHA = "0x5FbDB2315678afecb367f032d93F642f64180aa3"; // ← la que imprimió el script
const CHAIN_ID_SEPOLIA = 31337n;   // ← 31337n en red local · 11155111n en Sepolia

La n al final no es un error: es un BigInt de JavaScript. ethers v6 devuelve el chainId como BigInt, y un BigInt no es igual a un número normal (31337n === 31337 es false). El nombre CHAIN_ID_SEPOLIA se conserva igual que en la solución de referencia aunque en local valga 31337.

4.2 · El ABI. Miren la constante ABI: cinco líneas con las firmas de symbol, decimals, balanceOf, transfer y el evento Transfer. Es todo lo que la interfaz necesita saber del contrato. No hace falta tocarlo.

4.3 · Punto de control 2, desde la terminal. Antes de pelear con el navegador, comprueben que la dirección y la red están bien. El script hace las mismas lecturas que la dApp, con el mismo ABI:

$env:FICHA="0x5FbDB2315678afecb367f032d93F642f64180aa3"; $env:CUENTA="0xSU_DIRECCION"
npx hardhat run scripts/s12/comprobar-ficha.js --network localhost      # o --network sepolia

Salida esperada (real, de la preparación):

  red           : localhost (31337)
  contrato      : 0x5FbDB…  (2819 bytes de código)
  símbolo       : FUSB
  decimales     : 18
  saldo bruto   : 1000000000000000000000      <- lo que devuelve la cadena (entero)
  saldo legible : 1000.0 FUSB   <- formatUnits
  ETH p/ gas    : 10.0

Si dice En 0x… NO hay contrato en la red 31337, la dirección está mal copiada, están en otra red, o reiniciaron el nodo. Arréglenlo aquí: con esa dirección, la dApp tampoco funcionaría.

6
TODO 6 · ESCRITURA · transferEnviar y ESPERAR, con un mensaje en cada momento
Qué escribir (dentro del try del botón Enviar, en lugar de falta(…)):
const cantidad = ethers.parseUnits(monto, decimales); — «2.5» se vuelve 2500000000000000000n.
const tx = await contrato.transfer(dest, cantidad); — aquí MetaMask muestra la transacción y pide confirmar.
estado("Transacción enviada. Esperando confirmación… " + tx.hash.slice(0, 10) + "…", "pendiente");
const recibo = await tx.wait(); — aquí espera a que se MINE.
if (recibo.status === 0) { … "se revirtió" …; return; }, await refrescarSaldo(); y el estado verde con recibo.blockNumber.
El error que se combate: decir «listo» después de transfer() y antes de wait(). El primer await solo significa «enviada».
Punto de control 4: transfieran 2,5 FUSB a la dirección de un compañero (o a una segunda cuenta suya). Se ve amarillo «Confirma la transacción en la billetera…», luego amarillo «Transacción enviada. Esperando confirmación… 0x…», y al final verde «¡Listo! Transferencia confirmada en el bloque N.»; el saldo baja a 997.5. En red local todo pasa en menos de un segundo; en Sepolia, unos 12 segundos.
7
TODO 7 · manejarError(e)Un mensaje claro para cada caso
Qué escribir, en este orden, cada caso con estado(…, "error") y return:
a) Rechazo (estado 3): e.code === "ACTION_REJECTED" || e.code === 4001. El 4001 es el código de EIP-1193 («el usuario rechazó»); ethers v6 lo traduce a ACTION_REJECTED.
b) Revertida (estado 4): e.code === "CALL_EXCEPTION" || /revert/i.test(e.message || ""). Si existe e.receipt, la transacción se minó y el gas SÍ se pagó; si no existe, falló al simularla (estimateGas) y no se gastó nada. Díganlo en el mensaje.
c) Sin ETH para el gas: e.code === "INSUFFICIENT_FUNDS".
d) Cualquier otro: "Error: " + (e.reason || e.shortMessage || e.message).
Dato verificado: en ethers v6, cuando una transacción minada queda con status 0, tx.wait() no devuelve el recibo: lanza CALL_EXCEPTION con el recibo adjunto. Por eso la reversión se atrapa aquí y no en el if (recibo.status === 0), que queda como red de seguridad.

TODO 8 · EVENTOS · suscribirEventos()Que el saldo cambie solo
Qué escribir: contrato.on("Transfer", (from, to) => { if (from === cuenta || to === cuenta) refrescarSaldo(); });
Cómo lo compruebo en red local: con la dApp conectada, en la terminal 2 corran otra vez el script, ahora con la variable FICHA: no despliega nada, solo les acuña 100 FUSB más.

POR QUÉ «UNKNOWN CUSTOM ERROR»

La FichaUSB revierte con un error personalizado de OpenZeppelin, ERC20InsufficientBalance(sender, balance, needed). Como el ABI de la dApp no lo declara, ethers no sabe decodificarlo. Reto opcional: agreguen al ABI la línea "error ERC20InsufficientBalance(address sender, uint256 balance, uint256 needed)" y miren cómo cambia el motivo. Con MetaMask real el texto puede variar un poco según la versión; lo que se evalúa es que se clasifique como revertida.

¿Y UNA REVERTIDA YA MINADA?

Pasa cuando la simulación sale bien pero la ejecución real falla (el estado cambió entre medio), o cuando alguien fuerza el envío. En la red local, Hardhat rechaza incluso las transacciones forzadas que revertirían, así que ese caso se ve mejor en Sepolia. Su TODO 7 ya lo cubre: CALL_EXCEPTION con e.receipt.
